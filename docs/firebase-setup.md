# Form & Roar — הפעלת ניהול ואירוח ב־Firebase

פרויקט שאישר הבעלים: **formandroar-ae8f9**. שם התצוגה: **FormAndRoar**.

הגדרות אפליקציית ה־Web שמסר הבעלים נשמרו ב־`src/firebase-public-config.json`. אלה מזהים פומביים שמיועדים להופיע בדפדפן, לא מפתח מנהל. אין בפרויקט סיסמה, Service Account או private key. הגנת הנתונים תלויה בהפעלת Authentication ובהחלת Firestore Rules, ולא בהסתרת Web API key.

## 1. הפעלת כניסה לבעל האתר

ב־Firebase Console, בתוך הפרויקט:

1. פתח **Build → Authentication → Get started**.
2. תחת **Sign-in method**, הפעל **Email/Password** ושמור. אין צורך להפעיל כניסה בטלפון או ספקים אחרים עבור המימוש הנוכחי.
3. בלשונית **Users**, בחר **Add user** והוסף את `formandroar.contact@gmail.com` עם סיסמת כניסה לאתר שתבחר שם. זו סיסמה נפרדת מסיסמת Gmail. אל תשלח אותה בצ׳אט ואל תכניס אותה לקוד.
4. העתק את **User UID** של המשתמש שנוצר. הוא נדרש להגדרת הרשאת בעל האתר בסעיף הבא.

האתר אינו מציע הרשמה ציבורית. עצם קיומו של חשבון Authentication אינו מעניק הרשאת עריכה.

## 2. Firestore וכללי הרשאות

1. פתח **Build → Firestore Database → Create database** ובחר מיקום מתאים באירופה. התחל ב־**Production mode**.
2. פתח את לשונית **Rules**, העתק אליה את כל תוכן הקובץ [`firestore.rules`](../firestore.rules) ולחץ **Publish**. אל תחליף אותו בכלל שמאפשר כתיבה לכל משתמש.
3. ה־UID שמסר הבעלים כבר נקשר בכללים: **qIjs6PlvVATYYAbcprHopz5OYZG3**. לחשבון הזה אין צורך במסמך הרשאה נוסף. ההרשאה תופעל רק אחרי פרסום הכללים וכניסה תקינה לחשבון באתר.

ההרשאה מוגבלת לחשבון בעל האתר היחיד הזה. רשומות ישנות באוסף catalogAdmins אינן מעניקות גישה למשתמשים אחרים. לשינוי בעל החשבון יש לעדכן את ה־UID גם בכללים וגם ב־src/owner-config.json ולפרסם מחדש.

גולשים יכולים לקרוא רק מוצרים שפורסמו. ל־UID אין כוח בפני עצמו: Firebase חייב לאמת כניסה לחשבון ולהנפיק אסימון תקין. הקישור לניהול אינו מוצג לגולשים. אחרי התחברות לחשבון הבעלים דרך /admin, מופיע באותו דפדפן כפתור Manage website. מסך ההתחברות ניתן לפתיחה בכתובת הישירה, אבל ניהול הנתונים נותר מוגבל לחשבון הבעלים.

## 3. אירוח האתר

הקוד מוכן ל־Firebase Hosting, אך הגדרות Web אינן הרשאת פריסה: נדרשת כניסה של בעל הפרויקט ל־Firebase CLI או תהליך פריסה מורשה אחר.

במחשב בעל הפרויקט עם Node.js מתאים:

```sh
git clone https://github.com/izhak11134-sys/FootBall.git
cd FootBall
npm ci
npx firebase login
npm run firebase:deploy
```

הכניסה בפקודת `firebase login` נעשית בחשבון Google שמחזיק את הפרויקט ב־Firebase Console, לא באמצעות סיסמת חשבון האתר שנוצר ב־Authentication.

הקובץ `.firebaserc` מצביע על `formandroar-ae8f9`. בדוק שזה הפרויקט הנכון לפני אישור כניסה או פריסה. הפקודה בונה את האתר ופורסת אירוח וכללי Firestore בלבד; היא אינה פורסת Functions או מפעילה שירותי תשלום.

אחרי פריסה מוצלחת, ה־CLI יציג את כתובת האירוח. הכתובת הצפויה כברירת מחדל לפרויקט היא `https://formandroar-ae8f9.web.app`, אך היא אינה נחשבת פעילה או מאומתת עד שהפריסה ובדיקת הגלישה הושלמו.

Firebase Console מציג את מסלול הפרויקט, מכסותיו וזכאותו. יש לבדוק אותן בחשבון שלך; לא הוגדר חיוב ולא בוצעה רכישה מהשיחה.

## 4. שימוש באזור הניהול

אחרי הפעלת השירותים והפריסה, פתח **`/admin`** באתר (גם `/admin.html` הוא קובץ מקור תקין). הקישור אינו מוצג באתר הציבורי. שמור את כתובת הניהול כסימנייה בדפדפן.

- התחבר עם חשבון בעל האתר שנוצר ב־Authentication.
- **Add item** יוצר טופס חדש; הפריט אינו נשמר עד לחיצה על **Save to website**.
- בחר מצב, קטגוריה, פרטים, תמונה מותרת לשימוש, קישור מוכר, מדינות יעד ומיקום תצוגה. קישור אינו אישור לתוכנית שותפים בפני עצמו.
- **Publish this item to the website** מפרסם רק פריט בעל נתוני מוכר תקינים. טיוטה נשמרת בענן בלי להופיע לגולשים.
- שינויים שפורסמו נקראים מהמסד ומתעדכנים באתר המחובר בזמן אמת, ללא העלאה חוזרת של קוד. סדר התצוגה נקבע לפי **Display position**.
- אם מכשיר אחר שינה פריט בזמן העריכה, השמירה נעצרת ומבקשת לטעון את הגרסה השמורה לפני ניסיון נוסף.
- אפשר להסיר פריט, לייצא גיבוי נתונים, להתנתק ולשנות סיסמת חשבון אתר. ספק Authentication עשוי לדרוש כניסה מחודשת לשינוי סיסמה.

`/manage.html` ו־`/editor.html` נשארו כלי טיוטות מקומיים. הם אינם תחליף לאזור הניהול המחובר ואינם מפרסמים ל־Firestore. קובץ ה־HTML העצמאי להורדה הוא צילום מצב סטטי, ולא מסך ניהול Firebase.

## 5. הגדרות פרסום וחיפוש

לאחר אימות כתובת האתר, אפשר להעתיק את `.env.example` לקובץ `.env.local` ולהגדיר **SITE_URL** לכתובת ה־HTTPS האמיתית. הבנייה תוסיף כתובות canonical, נתוני שיתוף ומפת אתר.

השאר **SITE_INDEXABLE=false** כל עוד האתר מכיל הדגמות בלבד. שינוי ל־true הוא פעולה מפורשת של הבעלים כשהאתר מוכן לאינדוקס. קיים דף 404 אמיתי, ללא הפניית כל כתובת לא מוכרת לעמוד הבית.

אפשר להחליף את פרטי ה־Web באמצעות ארבעת משתני `VITE_FIREBASE_*` שבדוגמה. אין להכניס Service Account למשתנה שמתחיל ב־VITE: ערכים כאלה נכנסים לקוד הדפדפן.

## 6. בדיקות ומה עדיין דורש אימות

```sh
npm test
npm run test:rules
npm run test:hosting
```

בדיקות הדפדפן בונות גרסת בדיקה נפרדת ב־`dist-test` עם חיבור ענן כבוי, כדי לא לפנות לפרויקט האמיתי או לשלוח הודעות במהלך בדיקה. הבנייה הרגילה ב־`dist` משתמשת בהגדרות הפרויקט האמיתיות.

בדיקות הכללים משתמשות ב־Firestore Emulator עם מזהה דמו `demo-form-and-roar`, לא בפרויקט של המשתמש. הן דורשות Java 21 והורדת אמולטור רשמי. בסביבת השיחה ההורדה מ־`storage.googleapis.com` נחסמה; לכן בשלב זה אין לטעון שהכללים עברו בדיקות אמולטור או שהתחברות/כתיבה לפרויקט האמיתי אומתו.

נשמרה טיוטת הרשאות רשת ליעדי Firebase הנחוצים לבדיקות מתוך הסביבה. החלה דורשת בדיקה ושמירה בהגדרות הסביבה ולאחר מכן Publish לסביבה. פעולה זו נפרדת מפרסום האתר ב־Firebase.

בדיקת Firebase Hosting המקומית הורצה בהצלחה: נתיבי קטלוג, HTTP 404 אמיתי וכותרות אבטחה באזור בעל האתר. זו אינה פריסה לענן ואינה בדיקת הרשאות Firestore.
